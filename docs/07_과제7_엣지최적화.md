전체 표(TensorRT FP32, PyTorch GPU 포함): `out/latency.csv`

- **이 크기의 모델에서는 ONNX Runtime(CPU)이 가장 빠르다.** 계산량이 너무 작아서, GPU로 데이터를 보내고 커널을 띄우고 결과를 받아오는 고정 비용(약 0.35ms)이 계산 시간보다 크다. TensorRT 지연의 바닥값(MLP 0.38ms)이 바로 이 고정 비용이다.
- **PyTorch는 CPU·GPU 모두 프레임워크 부담이 크다.** 특히 GRU CPU는 10.6ms로, 같은 계산을 ONNX Runtime은 0.21ms에 한다.
- 배치 1과 4의 지연이 거의 같다. 공간 4개를 한 번에 묶어 보내면 공간당 비용이 1/4이 된다.
- p95가 평균의 1.1배 이내로, 한가한 보드에서는 지연이 안정적이다.

### GRU 정밀도 조합 (`out/gru_precision.csv`)

| 변형 | FP32 고정 층 | CO₂ 최대 차이 | 배치 1 지연 | 엔진 크기 |
|---|---|---|---|---|
| 전부 FP16 | 0 / 227 | 1.31ppm ❌ | 1.25ms | 635KB |
| 전부 FP32 (TF32 끔) | — | 0.0002ppm | 1.31ms | 791KB |
| **GRU FP16 + 출력 MLP FP32** | 9 / 227 | **0.71ppm** ✅ | **1.25ms** | 689KB |
| GRU 일부 FP32 + 출력 MLP FP16 | 7 / 227 | **290ppm** (결과 깨짐) | 1.28ms | 695KB |

- 오차는 출력 MLP에서 커진다. 모델은 정규화된 **변화량**을 내고, 이를 CO₂ 표준편차(213ppm)로 곱해 ppm으로 바꾼다. 그래서 FP16의 작은 반올림 오차(0.006)가 **213배로 확대**된다. 출력 MLP 9개 층만 FP32로 두면 기준을 통과하고, 속도는 그대로다.
- **GRU 반복 구조 안의 일부 층만 FP32로 묶으면 결과가 완전히 깨졌다**(최대 290ppm). 반복 루프 안에서 FP16·FP32가 섞이며 형 변환이 어긋난 것으로 보인다. **정밀도를 섞을 때는 실제 입력으로 결과를 반드시 검증해야 한다.** 빌드가 성공했다고 결과가 맞는 것은 아니다.

| 확인 기준 | 결과 |
|---|---|
| 변환 후 CO₂ 예측 차이 1ppm 이하 | **0.71ppm** (FP16 + 출력 MLP FP32) ✅ |
| 분류 결과가 바뀐 비율 0.1% 이하 | **0%** (사용 여부, 환기 경보, 이상 경보 모두) ✅ |
| 측정 조건 기록 | 위 표 ✅ |

## 3. 전력·GPU·메모리 (배치 4로 3초 연속 실행하는 동안)

| 모델 | 방식 | 보드 전체 전력 | CPU+GPU 전력 | GPU 사용률 |
|---|---|---|---|---|
| 대기 | — | **5.83W** | 1.55W | 0% |
| 예측 GRU | PyTorch CPU | 8.49W | 3.96W | 0% |
| | PyTorch GPU | 7.25W | 2.72W | 11% |
| | ONNX Runtime (CPU) | **10.14W** | 5.60W | 0% |
| | **TensorRT FP16** | **7.24W** | 2.61W | 44% |
| 이상 탐지 | ONNX Runtime (CPU) | 7.48W | 2.99W | 0% |
| | TensorRT FP16 | 6.90W | 2.44W | 11% |

| 모델 | ONNX 파일 | TensorRT FP16 엔진 | TensorRT 작업 메모리 | PyTorch GPU 최대 할당 |
|---|---|---|---|---|
| 예측 GRU | 218KB | 635KB (혼합 689KB) | 89MB | 9.4MB |
| 이상 탐지 | 145KB | 244KB | 4.9MB | 9.4MB |
| 사용 여부 MLP | 13KB | 59KB | 1.5MB | 9.3MB |
| 환기 경보 MLP | 15KB | 61KB | 1.5MB | 9.2MB |

- **ONNX Runtime(CPU)은 빠르지만 연속 실행 중 전력이 가장 높다**(GRU 10.1W, 대기보다 +4.3W). 기본 설정이 CPU 코어 여러 개를 동시에 돌리기 때문이다. TensorRT는 같은 일을 7.2W로 한다.
- GRU 엔진의 작업 메모리 89MB는 **최대 배치 4096**으로 만들었기 때문이다. 서비스용은 최대 배치를 8 정도로 줄이면 수 MB로 준다.
- 모델 네 개를 모두 올려도 가중치는 1MB, 작업 메모리는 100MB 이하다. 실제 메모리 대부분은 **PyTorch·CUDA 런타임 자체**(프로세스당 약 200MB, 과제 6 측정)가 차지한다.

## 4. 생각해 볼 점

**CPU로도 1ms면 충분한데 왜 변환하나**
- 이번 측정으로 보면 이 크기 모델은 **ONNX Runtime(CPU)이 가장 빠르다**(0.03~0.5ms). 지연만 보면 변환할 이유가 약하다.
- 그래도 변환하는 이유는 **같이 올라갈 다른 모델들** 때문이다. 로컬 LLM·임베딩 모델이 CPU를 점유하면 CPU 추론 지연이 크게 늘어난다(과제 6에서 팀원 작업 중 GRU CPU 지연이 9.9ms에서 80ms로 늘었다). GPU 경로는 이 영향을 덜 받는다(같은 상황에서 0.86 → 0.94ms).
- **전력**: 연속 추론 시 TensorRT가 ONNX Runtime CPU보다 2.9W 적다. 공간이 수십 개로 늘어 추론이 잦아지면 차이가 커진다.
- **공간 수 확장**: 배치 1과 4의 지연이 같으므로, GPU 경로는 공간이 늘어도 비용이 거의 늘지 않는다.

**GRU와 TCN 중 무엇이 변환 후 더 빨라지나**
- **TCN: PyTorch GPU 2.14ms → TensorRT 0.62ms (3.5배)**. **GRU: 1.10ms → 1.27ms (빨라지지 않음)**.
- TCN의 합성곱은 24칸을 **한꺼번에 병렬 계산**한다. TensorRT가 합성곱과 ReLU를 하나로 묶어(퓨전) 커널 수를 줄일 수 있다.
- GRU는 24칸을 **한 칸씩 차례로** 계산해야 한다(앞 칸의 결과가 다음 칸의 입력). 각 단계가 작은 행렬 곱이라 GPU를 다 쓰지 못하고, 반복 루프를 돌리는 부담이 남는다. PyTorch GPU는 이미 cuDNN의 GRU 전용 커널을 쓰고 있어서 TensorRT가 더 줄일 여지가 적다.
- 엣지 배포가 중요하면 **TCN 구조를 쓰는 편이 변환 이득이 크다.** 정확도 비교는 심화(B) 과제 3에서 할 일이다.

**평균보다 '느린 쪽 5%'가 더 중요한 이유**
- 서비스는 **매분 정해진 시각에 결과를 내야** 한다. 평균이 빨라도 가끔 크게 늦으면 그 분의 결과가 빠지거나 늦게 나간다. 경보는 늦으면 의미가 없다(과제 4).
- 보드를 여러 작업이 같이 쓰면 평균보다 **꼬리 지연이 먼저 나빠진다.** 과제 6 중 보드가 몇 분간 응답하지 않은 것이 극단적인 예다.
- 이번 측정은 한가한 보드에서 p95/평균이 1.1배 이내였다. 서비스 운영 중에는 p95를 계속 기록해 감시해야 한다(과제 8).

## 5. 결론 (과제 8 서비스 적용)

| 모델 | 서비스에서 쓸 실행 방식 | 이유 |
|---|---|---|
| 예측 GRU | **TensorRT FP16 + 출력 MLP FP32** (`engines/forecast_gru.fp16_headFP32.engine`) | 기준 통과(0.71ppm), GPU 경로라 CPU 경쟁에 강함, 전력 낮음 |
| 이상 탐지 오토인코더 | TensorRT FP16 | 경보 판정 변화 0% |
| 사용 여부·환기 경보 MLP | TensorRT FP16 | 분류 변화 0% |
| (예비) 전부 | ONNX Runtime CPU, **스레드 1개**로 제한 | GPU를 로컬 LLM이 점유할 때의 대안. 결과 차이가 사실상 0 |

- 모델 네 개를 합쳐도 매분 공간 4개 처리에 **약 3ms**(TensorRT, 배치 4)면 충분하다.
- 서비스용 엔진은 **최대 배치를 8로 줄여** 다시 만들어 작업 메모리를 줄인다.
- 측정 한계: 클럭을 고정하지 않았고(sudo 필요), ONNX Runtime은 CPU 실행만 측정했다. 스레드 1개 설정의 지연·전력은 과제 8에서 확인한다.
