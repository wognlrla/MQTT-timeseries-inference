# 과제 8. 상시 추론 서비스 v1 (초안)

**측정 조건**: Jetson Orin Nano Super, 25W, 2026-10-21 09:45 가동 시작. 입력은 합성 재생 데이터(seed 42 시험 주간을 현재 요일·시각에 맞춰 재생, 고장 17건 포함)이고, 실데이터 공간은 데이터 끊김 감시만 한다. 팀원(team2-2)의 별도 서비스(API 8090, MQTT 1884)와 포트를 나눠 같은 보드에서 함께 가동 중이다.
**결과 형식 문서**: `/srv/team/service_kit/INTERFACE.md`

## 1. 구성

```
[재생기 svc-simfeed]  합성 시험 주간 → 현재 요일·시각으로 매핑, 1분마다 발행 (sim/sensors/<공간>)
        │ MQTT (svc-mosquitto :1885, 서비스 계정만 쓰기)
        ▼
[수집기 svc-collector-sim]  과제 1 수집기와 같은 이미지·코드, 설정 파일만 다름 → InfluxDB sim_live
        │
        ▼
[추론 서비스 team2-svc (systemd)]  매분 15초
   ① 최근 4시간 원본 읽기 → ② 키트(service_kit): 과제 2 전처리 → 과제 3·4·5 모델 → 규칙
   ③ 경보 상태 갱신(중복 방지) → ④ MQTT 발행(retain) + 조회 API :8091 + InfluxDB service 버킷에 이력
        │
        └─ 실데이터(sensors 버킷: 실습실·사무실·사무실 밖·회의실): 데이터 끊김 감시만
```

| 구성 요소 | 자동 시작 | 메모 |
|---|---|---|
| svc-mosquitto, svc-simfeed, svc-collector-sim | Docker `restart: unless-stopped` | `/srv/team/service/docker-compose.yml` |
| 추론 서비스 | systemd `team2-svc` (`enabled`, `Restart=always`, 메모리 상한 1.5GB) | `/srv/team/service/service.py` |
| 추론 키트 | — | `/srv/team/service_kit/kit.py`. 다른 서비스도 import해서 쓸 수 있음 |

**왜 합성 데이터인가**: 모델은 합성 4개 공간(강의실 A·B, 회의실, 라운지)과 그 일정으로 학습했다. 실데이터 공간은 공간·일정이 달라 모델을 그대로 쓸 수 없다. 과제 규정("실데이터 3주 전에는 합성 데이터")에 따라 합성 시험 주간을 실시간처럼 재생했다. 요일·시각을 맞춰서 지금 9시면 시험 주간의 같은 요일 9시 수업이 재생된다. 심어 둔 고장 17건도 해당 요일·시각에 그대로 재생된다.

## 3. 학습과 똑같은 전처리

서비스는 학습 때 쓴 함수를 **그대로 불러다 쓴다**(`preprocess.clean_raw/to_grid`, `features.schedule_grid/static_feats`, `detectors` 규칙). 같은 규칙을 다시 짜지 않는다.

**일치 시험** (`service_kit/test_consistency.py`): 시험 기간 159개 (공간 × 시점)에서, 학습 함수로 만든 입력과 서비스가 **최근 4시간만 보고** 만든 입력을 비교했다.

| 입력 | 최대 차이 |
|---|---|
| 예측 모델 (과거 2시간 + 시각 + 앞으로 60분 일정) | **0** |
| 오토인코더 | **0** |
| 사용 여부·환기 분류기 | **0** |
| 예측 결과 (서비스 vs 과제 3 PyTorch) | 0.038ppm |

**전처리가 다르면 생기는 일**: 모델은 학습 때 본 입력 분포를 기준으로 판단한다. 예를 들어 서비스가 결측을 선형 보간으로 채우면(학습은 직전 값 채움), 끊겼다 돌아오는 순간의 값 모양이 학습 때와 달라진다. 서비스가 정규화 평균·표준편차를 서비스 기간 데이터로 다시 계산하면, 같은 900ppm이 다른 숫자로 들어간다. 이런 차이는 **오류 메시지 없이 예측만 조용히 틀어지게** 만든다. 시험 성적이 아무리 좋아도 현장 성능은 나빠진다. 그래서 같은 함수를 쓰고, 시험으로 입력 차이 0을 확인했다.

## 4. 제공 방식

- **MQTT** (포트 1885, 익명 읽기 전용): 상태·경보·실데이터·서비스 상태는 **retain**이라 **새로 접속한 구독자가 즉시 최신값 13개를 받았다**(확인함). 경보 변화만 `team2/svc/events`로 흐른다. 익명 발행은 거부된다(ACL).
- **서비스가 비정상 종료되면** 브로커가 `team2/svc/status`를 `{"online": false}`로 바꾼다(LWT). 시험 실행을 강제 종료했을 때 실제로 이렇게 바뀌는 것을 확인했다.
- **조회 API** (포트 8091): `/health`, `/spaces`, `/spaces/{space}`, `/spaces/{space}/forecast?minutes=30`, `/alerts`, `/events`, `/real`, `/docs`. 예: `GET /spaces/meeting/forecast?minutes=30` → `{"value": 670.4, "unit": "ppm", "base_time": "2026-10-21T09:45:00", ...}`

## 5. 장애 시험 (2026-10-21)

| 시험 | 결과 | 판정 |
|---|---|---|
| **계산 1회 실패** (09:47, `FAIL_NEXT`로 일부러 예외) | 09:47 주기 실패 기록(`failures: 1`, `last_error`) → **09:48 주기 정상** | ✅ |
| **수집기-sim 10분 정지** (09:49:25 ~ 09:59:26) | 회의실 09:58, 강의실 A·B 09:59 **`data_gap` 경보 발생**. 원인 추정: "수집기 정지 또는 연결 끊김"(수집기 상태 기록이 끊김) | ✅ |
| 수집기 재시작 → 정상 복귀 | 재시작 49초 뒤(10:00:15) **세 공간 모두 `data_gap` 해제**. 정지 중 10분 데이터도 **브로커가 보관했다가 모두 채워 넣음**(09:49~09:59 매분 1건, 유실 0) | ✅ |
| 서비스는 계속 동작 | 정지 중에도 매분 계산 성공(0.37~0.41초) | ✅ |
| 보드 재부팅 → 자동 시작 | systemd `enabled` + Docker `unless-stopped`. 수집 스택은 과제 1에서 재부팅 2회 확인. **서비스 포함 재부팅 시험은 아직 안 함** | ⏳ |

- **라운지는 10분 정지로는 경보가 나지 않았다.** 라운지는 5분마다 기록해서 끊김 기준을 15분(3번 연속 누락)으로 잡았기 때문이다. 기준을 10분으로 낮추면 기록 하나만 늦어도 헛경보가 난다. 공간마다 기록 주기에 맞춘 기준이 맞다고 판단한다.
- 데이터가 끊긴 동안에도 15분까지는 **직전 값으로 채워 예측을 계속**했다(학습과 같은 규칙). 그래서 이 동안 `co2_over_1000` 같은 경보가 낡은 값으로 유지됐다. 결과에 `filled_cells_2h`(채운 칸 수)를 넣어 사용하는 쪽이 신뢰도를 판단할 수 있게 했다.

## 6. 운영 판단: TensorRT 대신 ONNX Runtime

| 실행 방식 | 서비스 메모리 | 1주기 |
|---|---|---|
| TensorRT (과제 7 엔진) | **1,185MB** | 0.38초 |
| **ONNX Runtime CPU, 스레드 1개 (채택)** | **약 380~680MB** | 0.37~0.59초 |

- 같은 보드에서 팀원 학습(1.4GB)·팀원 서비스(0.5GB)가 함께 돌아 **여유 메모리가 1.3GB**였다. TensorRT를 쓰려면 CUDA 런타임이 필요해 메모리를 0.5GB 더 쓴다. 과제 6에서 메모리 부족으로 보드가 멈춘 적이 있어 이를 피했다.
- 과제 7에서 이 크기 모델은 ONNX Runtime이 가장 빨랐고, 결과 차이도 0.0002ppm이다. 메모리 여유가 생기면 `.env`의 `SVC_BACKEND=tensorrt` 한 줄로 바꿀 수 있다. TensorRT 실행이 실패하면 키트가 자동으로 ONNX Runtime으로 넘어간다.

## 7. 생각해 볼 점

**막 시작된 5분 칸(1~2분치만 있음)을 써도 되나** — 쓰지 않는다. 학습 때 5분 칸은 항상 5분치(1분 센서 기준 5개) 평균이었다. 1~2분치 평균은 잡음이 더 크고, 수업 시작처럼 빠르게 오르는 구간에서는 체계적으로 낮게 나온다. 서비스는 **마지막으로 끝난 칸까지만** 쓴다(09:23에 계산하면 09:20 칸이 마지막). 대신 결과가 최대 5분 늦다. `data_gap` 같은 규칙은 원본을 바로 보므로 늦지 않는다.

**같은 고장에 매분 경보를 보내면** — 한 시간에 60번 같은 알림이 오면 운영자는 알림을 끈다(과제 4). 그래서 경보마다 상태를 저장해 **처음 한 번(raised), 이어지면 30분마다(reminder), 풀리면 한 번(cleared)**만 보낸다. 상태는 파일에 저장해서 서비스가 재시작돼도 같은 경보를 다시 '새로 울림'으로 보내지 않는다.

**로컬 LLM이 이 서비스를 '도구'로 쓰려면 더 필요한 것**
- 지금 있는 것: 공간 이름, 기준 시각과 단위, 예측 불가·끊김의 **이유 문장**, 경보 이름과 기준값.
- 더 필요한 것: ① **예측 구간**(얼마나 확실한가, Chronos 보조 모델) ② **권장 행동**("창문 열기", "시설팀 연락") ③ "지난 1시간 경보 요약" 같은 **요약 엔드포인트** ④ 도구 설명용 **짧은 스키마**(OpenAPI `/openapi.json`는 이미 있음).

## 8-1. 재부팅 후 시계 점프 사고와 수정 (2026-10-26)

### 무슨 일이 있었나

보드를 재부팅한 뒤 약 12분 동안 아래 일이 차례로 일어났습니다.

1. **부팅 직후 보드 시계가 1970년이었다가, NTP 동기화로 2026년으로 점프했습니다.**
   - 컨테이너 시작 시각이 "56년 전"으로 표시된 것으로 확인했습니다.
2. **재생기(simfeed)가 메모리를 다 썼습니다.**
   - 직전 재생 시각(1970년)부터 현재(2026년)까지 **56년치를 한 번에 재생**하려고 했습니다.
   - CPU 89%, 메모리 4.0GB를 쓰고, 스왑 8GB도 가득 찼습니다.
3. **합성 데이터 수집기(svc-collector-sim)가 막혔습니다.**
   - 시계가 1970년이던 동안 쌓인 점들이 재시도 큐 맨 앞에 있었습니다.
   - InfluxDB는 이 점들을 보관 기간 밖이라 거부했습니다(HTTP 422).
   - 수집기는 같은 배치를 계속 다시 보내느라 **새 데이터를 하나도 쓰지 못했습니다**(큐 18,930건).
4. **상시 서비스는 계속 돌았지만 매분 실패했습니다.**
   - 입력 데이터가 없어서 `ValueError: No objects to concatenate`가 났습니다(실패 12회).
   - 서비스 프로세스 자체는 죽지 않았고, 데이터가 다시 들어오자 바로 정상으로 돌아왔습니다.

실데이터 수집기(`collector`)는 쌓인 큐가 없어서 영향이 없었습니다(쓰기 오류 0).
